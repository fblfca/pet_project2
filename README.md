# Прогноз отмены бронирования отеля

Учебный проект на реальных данных о бронированиях двух отелей. Я исследую качество
данных, сравниваю восемь алгоритмов классификации и проверяю, как выбор порога
прогноза влияет на условные потери отеля.

## Задача и данные

Цель — оценить вероятность отмены бронирования на момент его оформления.
Целевой столбец: `is_canceled` (1 — отменено, 0 — нет).

Использован набор [Hotel Booking Demand](https://www.kaggle.com/datasets/jessemostipak/hotel-booking-demand),
основанный на [публикации авторов данных](https://doi.org/10.1016/j.dib.2018.11.126).
В нём 119 390 бронирований городского и курортного отелей. Исходный CSV сохранён
в `data/raw/`. Работа с ним началась с исследования в ноутбуке
`notebooks/01_data_exploration.ipynb`.

## Этапы работы

1. Исследование структуры, пропусков, распределений и связей с целевой переменной.
2. Проверка доступности признаков в момент прогноза и исключение утечки.
3. Обработка числовых и категориальных признаков внутри `Pipeline`.
4. Сравнение Logistic Regression, SVM, KNN, MLP, Random Forest, CatBoost,
   LightGBM и AdaBoost.
5. Сопоставление KFold и StratifiedKFold при одинаковом числе фолдов.
6. Анализ Accuracy, Precision, Recall, F1, ROC-AUC, PR-AUC/AP и разницы между качеством
   на тренировочных и проверочных фолдах.
7. Учебный расчёт потерь при разных порогах вероятности.

## Запуск

Проверено на Python 3.14. Из корня проекта:

```bash
python -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements-ml.txt
python -m src.pet_project2.experiment
jupyter notebook notebooks/02_model_experiments.ipynb
```

На Linux/macOS активация окружения: `source .venv/bin/activate`.
Сначала запусти ячейки ноутбука 02: там находятся сравнение моделей и графики.
Затем скрипт обучает выбранную LightGBM на полном train и сохраняет метрики в
`reports/`, а обученный Pipeline — в `artifacts/best_model.joblib`.

## Что важно в эксперименте

`reservation_status` и `reservation_status_date` сообщают об исходе брони.
`assigned_room_type`, `booking_changes` и `days_in_waiting_list` могут измениться
после её создания. Эти поля исключены из модели. Заполнение пропусков, кодирование
категорий и масштабирование выполняются внутри кросс-валидации.

Восемь моделей сравниваются на 8000 строках обучающей выборки из-за разной
стоимости вычислений. Затем победитель обучается на всей обучающей части.
Отложенные 20% используются для итоговой оценки. Значения в таблице сравнения
могут измениться при другом случайном разбиении.
Перед разделением удаляются 31 994 полностью совпадающие строки. В данных нет
уникального ID брони, поэтому это решение остаётся допущением исследования.

## Результаты

После удаления точных дублей осталось 87 396 записей. На одинаковой выборке из
8000 строк наибольший средний ROC-AUC по StratifiedKFold показал LightGBM —
**0,891**. После обучения на 69 916 строках train итоговый ROC-AUC на 17 480
отложенных строках составил **0,904**. При стандартном пороге 0,5:
Accuracy — **0,838**, Precision — **0,738**, Recall — **0,637**, F1 — **0,684**,
PR-AUC/AP — **0,784**.

| Модель | ROC-AUC | PR-AUC/AP |
|---|---:|---:|
| LightGBM | 0,895 | 0,762 |
| CatBoost | 0,891 | 0,759 |
| RandomForest | 0,889 | 0,753 |
| MLP | 0,863 | 0,705 |
| SVM | 0,863 | 0,718 |
| AdaBoost | 0,855 | 0,682 |
| LogisticRegression | 0,846 | 0,666 |
| KNN | 0,824 | 0,641 |

В таблице показан отложенный тест после обучения каждой модели на 8000 строках.
PR-AUC здесь рассчитан как Average Precision (AP). Он дополняет ROC-AUC,
показывая компромисс между Precision и Recall.

Для учебного соотношения стоимости FN:FP = 200:20 порог 0,1 был выбран на
валидационной части train. На тесте он дал Recall **0,976** и Precision **0,450**.
Расчётные потери составили 137 160 условных единиц против 370 480 при пороге
0,5. Цена этого выбора — 5 728 ложных тревог вместо 1 084. Подробный разбор
и ограничения есть в `reports/conclusions.md`.

Отдельный порог **0,35**, выбранный по F1 на валидации, повысил тестовый F1
с **0,684** до **0,710**, а Recall с **0,637** до **0,788**. Precision при этом
снизился с 0,738 до 0,647. Улучшение одной метрики сопровождается компромиссом
по другой — поэтому итоговый порог зависит от цели отеля.

После запуска скрипта основные файлы:

- `reports/model_comparison.csv` — шесть метрик, включая PR-AUC/AP;
- `reports/cv_folds.csv` — метрики на каждом фолде, включая train/validation;
- `reports/threshold_costs.csv` — условная стоимость ошибок при разных порогах;
- `reports/summary.json` — лучшая модель, параметры и метрики при трёх порогах;
- `reports/figures/` — графики сравнения, ROC- и PR-кривые.

Для иллюстрации бизнес-решения я принял FN = 200 и FP = 20 условных единиц.
Это **не реальные расходы отеля**. Порог подбирается на валидационной части train,
а затем применяется к отложенному test.

## Ограничения

Данные получены только из двух отелей. Для проверки прогноза на новых периодах
нужна дата создания бронирования, которой в наборе нет в явном виде. Кроме того,
доступность каждого признака на момент прогноза должна быть подтверждена в
реальной системе бронирований. Подробнее — в `reports/methodology.md`.
